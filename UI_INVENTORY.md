## 3.5 API contracts the UI depends on

- `atlasFetch<T>(path, token, sessionId)`

- `atlasHealth()`

- browser: `NEXT_PUBLIC_ATLAS_API` or `/api`

## 3.6 Theme system audit

Source files:

- `atlas-hcm-next/app/globals.css`
- `atlas-hcm-next/app/page.tsx`

Current theme architecture:

| Theme concern | Current implementation |
|---|---|
| Theme engine | CSS custom properties in `:root` |
| Active theme switch | `data-theme="light"` / `data-theme="dark"` |
| Accent switch | `data-accent="blue" | "emerald" | "slate"` |
| Density switch | `data-density` + `density-standard/compact/comfortable` classes |
| Persistence | `localStorage["atlas.ui.preferences"]` |
| DOM sync function | `syncWorkspaceThemeDom(themeMode, themeAccent, uiDensity)` |
| Session persistence | `localStorage["atlas.session"]` |
| Quick-add reference persistence | `localStorage["atlas.employee.reference.values"]` |

Current theme tokens already present:

- surface / elevated / glass surfaces
- text-primary / text-muted
- border-subtle
- shadow-soft / shadow-extruded
- accent-primary / accent-danger
- control heights
- card/control radii
- sidebar width / topbar height

Conclusion:

- The app already has a usable design-token foundation.
- The theme switcher is not a blank slate; it should be preserved and formalized, not replaced recklessly.

## 3.7 Structural findings

1. The UI is effectively a single-route monolith with many feature states inside one file.
2. Business capability is broad and already wired to backend contracts.
3. The best rewrite strategy is shell-first, module-by-module, while preserving the existing API layer.
4. The highest-risk areas are:
   - sidebar and shell layout
   - modal layering / portal interactions
   - dense form screens with mixed responsibilities
5. The theme/token system is good enough to evolve into the Step 4 design foundation.
